# TrueBooks

A small finance team's monthly close usually starts the same way: open four
exports — bank feed, payment-gateway settlement report, P&L from the books,
payroll register — and cross-check them by eye. TrueBooks is a demo of what
that process looks like when a language model handles the *judgment calls*
(what is this transaction?) while ordinary Python handles every *number*
(does this deposit match that payout, to the rupee?).

That split is the whole design: an LLM can mislabel a transaction and an
evaluation script will catch it later. If an LLM is allowed to compute a
number instead, a wrong one can slip into the books silently. So arithmetic
never touches the model here — only categorization does.

## What it actually does

1. Reads a bank feed, a settlement report, a P&L export, and a payroll
   register — four files that don't agree with each other by default.
2. Matches each bank deposit to the settlement payout that produced it,
   accounting for the gap between gross (what the report shows) and net
   (what the bank actually receives, after fees and tax).
3. Categorizes each transaction against a small accounting knowledge base,
   using retrieval so the decision is traceable to a written rule instead of
   a black-box guess.
4. Refuses to force a match or a category it isn't confident about — those
   go to a review queue with the specific reason attached, not just a
   generic "flagged" status.
5. Scores itself against held-out ground truth, so the numbers below are
   measured, not asserted.

## Results

Measured on synthetic data generated by `src/generate_data.py` (246 records
across all four sources).

| Metric | Result | Measured on |
|---|---|---|
| Deposits auto-matched to a settlement | 66.7% | all bank deposits |
| Match correctness, auto-matched deposits | 100% (18/18) | auto-matched subset |
| Categorization accuracy, mock model | 100% | P&L slice only, 11 records |
| Categorization lift from knowledge-base retrieval, real model | +46.4% | ambiguous vendor memos, `gpt-4o-mini` |
| Sent to human review | 33.3% | all bank deposits |

Two things worth being upfront about:

- **The 100% categorization number is small-sample.** It's measured on 11
  P&L records with ground-truth labels, not the full 246-record set. Read it
  as "correct on every labeled example we have," not "correct 100% of the
  time in general."
- **That same number is inflated by construction.** The knowledge base is
  built from the same vendor list as the test data, so retrieval usually
  finds an exact rule. The metric that isn't inflated this way is the
  +46.4% lift figure — it compares the same model *with* and *without*
  retrieval on genuinely cryptic memos (`FACEBK *7H2K9`, `SHENZHEN MFG CO`),
  and that gap is the real signal. Full breakdown in
  [`CASE_STUDY.md`](CASE_STUDY.md).

## Why deposits don't just match on amount

Three things make bank-to-settlement matching harder than `amount == amount`:

- **Gross vs. net.** The settlement report shows the gross sale amount; the
  bank shows what's left after the payment processor's fee and tax. The
  engine recomputes the expected net and checks it to the paisa — anything
  off gets a shortfall figure attached, not just a "no match" flag.
- **Settlement lag.** A payout initiated today doesn't land in the bank for
  a few days. Matching happens over a date window, not an exact date.
- **Risk holds.** Some deposits arrive short of the expected net because the
  processor is holding part of it in reserve. TrueBooks recognizes this
  pattern specifically (`partial_reserve`) rather than lumping it in with
  ordinary mismatches.

## Architecture

```
  Bank feed   Settlement report   P&L export   Payroll register
      │              │                 │              │
      └──────────────┴────────┬────────┴──────────────┘
                               ▼
                    Deterministic reconciliation
                    (gross/net math, date-window
                     matching — no LLM involved)
                               ▼
                    ┌──────────┴──────────┐
                    ▼                     ▼
              Auto-matched            Needs review
                    │                     │
                    ▼                     │
          RAG-grounded categorization     │
          (LLM judgment, cited to a       │
           knowledge-base rule)           │
                    │                     │
                    └──────────┬──────────┘
                               ▼
                  Scored against ground truth
                       (src/evaluate.py)
```

## Running it

No API key required — the default run uses a deterministic mock model, so
you can clone and try the full pipeline for free.

```bash
pip install -r requirements.txt

python src/generate_data.py     # synthesize the four messy source files + answer key
python src/knowledge_base.py    # build the accounting rule base
python src/reconcile.py         # match deposits to settlements
python src/evaluate.py          # score against ground truth, print exceptions
python src/evaluate_kb.py       # measure the retrieval lift specifically
streamlit run src/app.py        # browse results in a dashboard
```

To swap the mock for a real model, copy `.env.example` to `.env` and set
`OPENAI_API_KEY`.

## Code layout

| File | Responsibility |
|---|---|
| `src/schema.py` | Chart of accounts used for categorization |
| `src/generate_data.py` | Builds the synthetic messy data and its ground truth |
| `src/knowledge_base.py` | Builds the retrieval knowledge base |
| `src/policy_rag.py` | Retrieval logic over the knowledge base |
| `src/model.py` | Swaps between the mock model and a real provider |
| `src/categorize.py` | The only place the LLM is called — judgment, never arithmetic |
| `src/reconcile.py` | Deposit-to-settlement matching, entirely deterministic |
| `src/evaluate.py`, `src/evaluate_kb.py` | Scoring against ground truth |
| `src/app.py` | Streamlit dashboard |

## Scope, on purpose

- **No fine-tuning.** Prompting plus retrieval plus a real evaluation loop
  is easier to audit than a trained model, and audit-ability is the point
  of a finance tool.
- **No AR/AP or inventory modules yet.** The matching pattern here (deposit
  ↔ payout) generalizes to invoice ↔ payment or stock snapshot ↔ recorded
  COGS, but this project goes deep on four sources instead of wide across
  seven.
- **Retrieval is intentionally simple.** It's built behind a small
  interface so it can be swapped for hybrid search or reranking later, and
  so human corrections can eventually feed back into the knowledge base
  instead of being thrown away.

See [`CASE_STUDY.md`](CASE_STUDY.md) for the full writeup, including where
this would likely break on real, non-synthetic data.
